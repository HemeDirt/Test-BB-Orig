# РАБОТА С QWEN CODER: протокол, контракт и схема данных живых партий

*Документ для пользователя и для первого сообщения кодеру. Собран 2026-10 после трёх неудачных
сессий с кодером и переезда симуляций из чатов в локальную среду.*

## 0. Как это устроено на самом деле (просто и коротко)

- **Модель думает на сервере, а файлы и команды живут на твоём компьютере.** Когда кодер «гоняет
  симуляцию» или правит код, процессы идут локально — поэтому нагрузжен твой ПК. Это не обман и не
  поломка: так устроены все локальные кодинг-агенты. В сеть уходит только текст запросов и ответов модели.
- **GitHub не обязателен вообще.** Он нужен лишь как внешнее хранилище и история изменений. Локально
  историю можно вести простым `git` без всякого GitHub, а можно и вовсе zip-копиями папки перед
  каждой крупной сессией. Ничего из этого не требует навыков сверх «скопируй папку».
- **Папка проекта должна существовать ДО старта кодера.** Половина твоих прошлых бед (переносы,
  «скачай и настроим отдельно») возникала потому, что агент начинал в общей среде и потом пытался
  её переубрать. Если папка одна и она твоя, переносить нечего.
- **Режим разрешений.** Без согласований агент может удалить лишнее; с согласованием каждого чиха —
  вязнет. Рабочий компромисс: согласование только на УДАЛЕНИЕ и на выход за папку проекта, плюс
  правило «показывай дифф до применения» (см. контракт). Если интерфейс даёт только «всё или ничего»,
  выбирай «всё» ВНУТРИ одной папки проекта с заранее сделанной zip-копией: тогда худшее, что
  случится, — распакуешь копию обратно.

## 1. Подготовка за пять минут (до первого сообщения кодеру)

1. Создать папку, например `C:\BB_SIM\` (или `~/BB_SIM/`).
2. Скопировать в неё из нашей рабочей области два файла: `ЗАДАНИЕ_НА_СИМУЛЯЦИЮ_ББ.md` (переименовать
   в `SPEC.md`) и этот документ (переименовать в `PROTOCOL.md`).
3. Сделать zip-копию папки (пустой пока) и положить её ВНЕ папки проекта: это точка отката.
4. По желанию, три команды локального git без GitHub: `git init`, `git add -A`, `git commit -m start`.
   Дальше после каждой принятой работы: `git add -A && git commit -m "этап N"`. Это даёт историю и
   откат одной командой `git checkout .` если агент натворит лишнего.
5. Открыть кодер УЖЕ В этой папке и начинать разговор.

## 2. Контракт: вставить первым сообщением кодеру дословно

Правила работы над этим проектом (обязательны):
1. Рабочая папка одна — текущая. Не создавай других папок проекта, не предлагай скачивания,
   переносы и «настройку окружения вне папки», не трогай ничего за её пределами.
2. Каждое изменение кода показывай диффом (было → стало) ДО применения и применяй сам одним
   действием. Сразу после применения запускай проверку и вставляй её фактический вывод.
3. Никогда не удаляй и не переименовывай файлы без моего явного «да» на конкретный файл.
4. Не пиши «готово», «изменено», «исправлено», если не можешь показать вывод запуска или содержимое
   файла ПОСЛЕ изменения. Слова без вывода считаются несделанными.
5. Все допущения и решения записывай в DECISIONS.md по одной строке; все прогоны сохраняй в
   results/*.json; отчёты собирай скриптом report.py, а не руками.
6. Держи в контексте только текущую задачу; всё остальное читай из SPEC.md и DECISIONS.md по запросу.
7. Сдавай этапы по одному: ядро → валидатор и фазз → матрицы → отчёты → калибровка по живым данным.
   Не начинай следующий этап, пока я не написал «принято».
8. Если в правилах игры чего-то не хватает — задай ОДИН вопрос и жди ответа; не выдумывай механики.

## 3. Этапы и как пользователю проверять каждый (без веры на слово)

| Этап | Что сдаёт кодер | Твоя проверка одной командой |
|---|---|---|
| 1. Ядро | `bbsim.py`: партия по сиду, лог и STATS в конце | `python3 bbsim.py 1 8` — глазами смотришь лог: раскрытия, броски, таблицы, Жатва |
| 2. Валидатор и фазз | `validate.py`, `fuzz_test.py` | `python3 fuzz_test.py` — ждёшь строку «0 нарушений» |
| 3. Матрицы | `matrix.py` с конфигурациями из SPEC.md, пишет results/*.json | `python3 matrix.py base_n8` — смотришь, что json появился и в нём end/deaths/alive |
| 4. Отчёты | `report.py` собирает md-таблицы из json | `python3 report.py` — открываешь отчёт, сверяешь пару чисел с json вручную |
| 5. Калибровка | подгон профилей ботов под живые партии (раздел 5) | сравниваешь end и причины смертей с живой партией из заметок |

Дополнительный стоп-сигнал: если на любом этапе кодер предлагает «сначала скачайте/перенесите/
создайте отдельную папку для запуска» — отвечать «нет, пункт 1 контракта» и требовать запуска на месте.

## 4. Чек-лист «не верю на слово» (против прошлых проблем)

- Просишь изменение → получил дифф и вывод запуска? Нет = не сделано.
- Файл, который «изменён», открывается и содержит новое? Проверь сама одним открытием.
- Цифры в отчёте сходятся с json в results/? Сверь две-три строки руками.
- Папка проекта не обросла лишним? Один взгляд на список файлов после этапа.
- Есть ли запись в DECISIONS.md по каждому спорному месту? Нет = решение не принято, а угадано.

## 5. Схема данных живой партии (для калибровки «как живые игроки»)

Каждую живую партию достаточно записывать в один json по схеме ниже; симулятор затем подбирает
параметры ботов (страх, терпеливость, доли агрессии/помощи/театральности, усталость) так, чтобы
распределения симуляции совпадали с живыми: длина в циклах и минутах, доли причин смертей,
число раскрытий к финалу, число споров, частота применения спецкарт и профессий.

```json
{
  "meta": {"date": "2026-10-01", "N": 5, "situation": "pole",
           "house": ["harvest_late"], "explain_min": 12, "total_min": 47, "disputes": 3},
  "players": [{"seat": 1, "archetype_note": "dnd-master"}, {"seat": 2, "archetype_note": "newbie"}],
  "events": [
    {"c": 1, "p": 2, "t": "reveal", "cards": ["ТЕЛО-07", "ИСТ-12"]},
    {"c": 1, "p": 2, "t": "declare", "kind": "RPDI-kill", "base": "ПРОФ-03", "target": 4},
    {"c": 1, "p": 2, "t": "roll", "d20": 7, "table": "A", "outcome": "fail_self_1"},
    {"c": 1, "p": 2, "t": "or_delta", "who": 2, "delta": 1},
    {"c": 1, "p": 5, "t": "ghost_shadow", "card": "ТЕНЬ-08", "target": 3},
    {"c": 1, "t": "cycle_end", "alive": [1, 2, 3, 4, 5], "harvest": null},
    {"c": 3, "p": 2, "t": "death", "cause": "selfkill"},
    {"t": "game_end", "cycle": 5, "alive": [1, 4]}
  ]
}
```

Правила записи: событие `declare` пишется ДО броска; `roll` содержит сырое значение и таблицу;
смерти всегда с причиной (wounds/kill/selfkill/harvest/link/sniper/quota/anvil/vote/pressure/forced);
временные метки не обязательны, но `total_min` и `disputes` очень желательны — ими калибруется
модель времени и модель споров.

## 6. Чего не делать (уроки прошлых сессий)

- Не начинать кодер в общей/домашней папке «на время» — только в папке проекта.
- Не соглашаться на скачивания проекта и «отдельную папку запуска».
- Не принимать отчёты без вывода команд; не принимать «я поменял» без диффа.
- Не давать удалять файлы пачками: только по одному и только с твоим «да».
- Не смешивать этапы: пока ядро не принято, матрицы не гоняются.
- Не терять DECISIONS.md: это твоя страховка от смерти контекста у кодера — он, как и чаты,
  переполняется, а файл остаётся.
